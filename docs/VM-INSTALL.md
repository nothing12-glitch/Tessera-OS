# TesseraOS у віртуальній машині

Три шляхи, і вони різняться не «швидкістю», а тим, що саме ти отримуєш.
Обирай за тим, скільки в тебе є місця і чи потрібен тобі справжній образ.

| Шлях | Що отримуєш | Потребує | Час |
|---|---|---|---|
| 1. Пакунок на наявний образ | оформлення MD3 (RRO-оверлеї) поверх будь-якого Android 13+ у VM | adb + 2 ГБ | ~15 хв |
| 2. Збірка образу ROM | самостійний `.img` TesseraOS, який запускається без чужої бази | Linux, 400+ ГБ місця (600+ рекомендовано), 16 ГБ RAM + 16 ГБ swap | 5–9 год перший прохід |
| 3. Готовий образ із релізу | те саме, що шлях 2, без збірки | 20–40 ГБ | хвилини завантаження |

Три шляхи — це VM. Для справжнього телефона відповідь коротша й інша за ціну
помилки: тема ставиться вже сьогодні, образу для телефона ще немає, а наслідок
помилки — не «перестворити VM», а розблокований завантажувач. Тому окремий
розділ «На справжньому телефоні» — у кінці цього документа.

Шлях 3 ще не існує: перший образ з'явиться разом із віхою M1
([ARCHITECTURE.md](ARCHITECTURE.md) — roadmap), коли шлях 2
відпрацює на білд-боксі. Поки що в GitHub Release лежить пакунок із шляху 1 —
його збирає `.github/workflows/release.yml`.

> **Що саме в пакунку змінилося.** Чинний опублікований `v15.22.2.3` — це
> **лише тема**: три RRO-оверлеї, два інсталятори, нуль APK. Від 2026-10-25
> власних застосунків у продукті немає (README, §«Чому без наших
> застосунків»), тож інсталятор ставить тільки оверлеї. Попередній
> `v15.22.2.2` — сім наших APK + тема; він лишається на сторінці релізів,
> але більше не «найновіший».

## Шлях 1. Пакунок поверх наявного образу

Це не заміна ROM, а те, чим можна скористатися сьогодні: та сама палітра й
форма іконок Material Design 3, але на чужій базі. Гостьова система має бути
**Android 13 або новіше (API 33+)** — на старішому оверлеї теми не застосуються,
і це не наша примха, а вимога ресурсів бази.

1. Завантаж пакунок `tessera-vm-<версія>.tar.xz` зі
   [сторінки релізів](https://github.com/nothing12-glitch/Tessera-OS/releases)
   і звір суму з `<...>.tar.xz.sha256`.
2. Розпакуй. Всередині: `apks/`, `apps.list`, `install-on-vm.sh`,
   `install-on-vm.ps1`, `README.txt` і `overlays/` з `packages.list` — якщо
   збірка оверлеїв удалася, пакунок має і тему.
3. Запусти гостьову систему так, щоб хост бачив її через adb
   (для емулятора — `-ports` або стандартний `emulator-5554`; для VM із мережевим
   adb — `adb connect <IP>:5555`).
4. Встанови:

   ```bash
   ./install-on-vm.sh              # Linux, macOS, Git Bash
   ```
   ```powershell
   .\install-on-vm.ps1             # Windows
   ```

5. Перезавантаж гостьову систему: `adb reboot` — static-оверлеї теми
   перечитуються лише на ранньому завантаженні.

Скрипт робить чотири речі й робить їх найкращими спробами, а не «або все, або
програш»: ставить APK з реєстру, призначає `HOME`, `ROLE_DIALER` і `ROLE_SMS`,
видає відсутні дозволи й вмикає оверлеї. Список APK він читає з `apps.list`
поруч зі скриптом — того самого реєстру, який використовує CI. Від 2026-10-25
той реєстр закритий, тому в чинному пакунку перші три пункти не роблять нічого
і залишається лише тема; дії з ролей спрацюють тільки для тих пакетів, які
справді встановились. Кожне «увага» в кінці — це рядок, який варто перечитати:
наприклад, роль набору не доступна на образі без телефонії.

**Якщо щось пішло не так**

- `.\install-on-vm.ps1 -DryRun` показує повний план (APK, ролі, дозволи) без
  жодної команди на пристрої — корисно перевірити, чи скрипт взагалі бачить пакунок.
- PowerShell видає «Unexpected token» на українських рядках — файл втратив
  UTF-8 BOM. Перекачай пакунок; редагуй його лише в кодуванні «UTF-8 with BOM».
- `adb` не бачить гостьову систему: `adb kill-server && adb start-server`, для
  мережевого adb — `adb connect <IP>:5555`.
- «гостьова система на API …: тема розрахована на Android 13+» — образ старий;
  сам скрипт на цьому не зупиняється (раніше зупиняв), але оверлеї на такому
  образі можуть не застосуватися.
- `cmd overlay не зміг увімкнути os.tessera.theme.*` — приватні ресурси
  framework (`config_*`, `Theme.DeviceDefault_*`) RRO приймає лише від
  оверлеїв, підписаних платформним ключем образу. Наш тестовий ключ ним не є,
  тому на чужій базі тема може не застосуватися: у власному образі з дерева
  AOSP static-оверлеї лежать у `/product/overlay` і працюють без діалогів.
  Це саме той пункт, якого ще не перевірено на живому пристрої.

**Що перевірити далі**

```bash
adb shell cmd overlay list | grep tessera            # -> три увімкненні os.tessera.theme.*
```

## Шлях 2. Справжній образ ROM

Образ збирається лише на Linux: AOSP build system не працює на Windows і macOS
нативно (див. [BUILD.md](BUILD.md) — там і повний список вимог). Іронія, яку
варто сказати вголос: **білд-бокс — це теж віртуальна машина**, і для багатьох
це єдиний спосіб отримати образ TesseraOS без виділеної машини.

```bash
# усередині Ubuntu 24.04 з 400+ ГБ диска і 16+ ГБ RAM
build/scripts/bootstrap.sh
build/scripts/new-tree.sh lineage-22.2      # база + наш шар через local_manifests
build/scripts/check-build-refs.sh --tree .  # секунди замість години втраченої збірки
vendor/tessera/os/build/scripts/build-emulator.sh tessera_x86_64-userdebug
```

Скрипт спершу готує наші APK (`prepare-app.sh` читає реєстр
`build/scripts/apps.list`), потім робить `lunch` і `m`. Образи лягають в
`out/target/product/emu64x/` — каталог названий за `PRODUCT_DEVICE`, тобто за
платформою емулятора, а не за назвою нашого продукту.

Запуск отриманого образу — `run-avd.sh` (Android Emulator, найнадійніший шлях,
бо образ і зібрано під `androidboot.hardware=ranchu`):

```bash
build/scripts/run-avd.sh --api 35 --image out/target/product/emu64x
```

### Чому не ISO для VirtualBox чи VMware

Конфіг платформи, який ми успадковуємо (базовий `device/generic/goldfish/board/
emu64x`), дає партиційні образи (`system.img`,
`vendor.img`, `userdata.img`, `super.img` і `kernel-ranchu`), а не завантажувальний ISO з
інсталятором. Щоб образ завантажувався з віртуального CD/DVD, потрібен інший
шар: установник і bootloader у стилі Android-x86. Цього в TesseraOS ще немає, і
робити його «на око» без живого білду — означає писати скрипт, який ніхто не
перевіряв. Тому чесна позиція:

| Гіпервізор | Статус |
|---|---|
| Android Emulator (QEMU всередині) | підтримано: `run-avd.sh` |
| QEMU/KVM напряму | технічно той самий `ranchu`, але cmdline ядра й initrd ще не перевірені на живому образі |
| VirtualBox, VMware | потребує завантажувального ISO — роботи в плані, не обіцянка |

Якщо потрібен саме VirtualBox, наразі єдиний робочий варіант — шлях 1 поверх
наявного образу Android 13+ з цього ж розділу.

Про прискорення на Windows (AEHD / «Платформа гіпервізора Windows») і чому
емулятор без нього не стартує — окремо і детально в
[EMULATOR.md](EMULATOR.md).

## Шлях 3. Готовий образ

Коли перший успішний білд шляху 2 трапиться, `.img` пакуються в
`tessera-x86_64-<ver>.tar.xz` і кладуться в той самий GitHub Release: файли
образу політика репо тримати в гілці забороняє (`policy.yml`), а Release —
легальне місце для них. Розпакуй і вкажи `run-avd.sh --image <каталог>`.

## На справжньому телефоні

Питання «а поставити це на телефон» — найчастіше, тому відповідь тут і без
обіцянок. Вона розпадається на дві різні речі.

**Тема — ставиться сьогодні.** Пакунок шляху 1 не є ROM: це три RRO-оверлеї,
які `adb` кладуть поверх *будь-якого* Android 13+ (API 33+) — і на телефоні теж.
Треба лише «Параметри розробника» + «Налагодження через USB» і 2 ГБ вільного
місця. Команди — ті самі, що у розділі «Шлях 1»; телефон для adb виглядає як
звичайний `device` у `adb devices`.

**Сам ROM — не ставиться, бо його ще немає.** TesseraOS збирається під
`x86_64` (дошка `emu64x`), а телефон — це `arm64` плюс власний пристрійний
дерево (драйвери дисплея, модема, камери). Порт на реальний пристрій — це
окрема робота з LineageOS-деревом саме твоєї моделі, а не перемикач у нашому
конфігу. Жодного `.img` для телефону в релізах немає, і перший з'явиться лише
тоді, коли шлях 2 відпрацює на білд-боксі (віха M1).

Перед тим, як взагалі думати про розблокування завантажувача, — ці наслідки
не оборотні:

| Ризик | Що саме стається |
|---|---|
| Дані | розблокування стирає пристрій повністю; резервну копію роблять ДО, а не «потім» |
| Samsung | тригер Knox не скидається нічим: зникають Samsung Pay/Secure Folder, а частина банківських застосунків відмовляється працювати назавжди |
| Verified boot | стан стає `orange` (на образі з цього репо виміряно саме `orange`) — застосунки, що перевіряють цілісність, на це реагують відмовою |
| Strim DRM | Widevine зазвичай падає з L1 до L3: потокове відео більше не 1080p |
| «Цегла» | прошивка невідповідного образу зупиняє завантаження; без робочого fastboot/recovery й стокового образу виробника у запасі повертати нічим |
| Google-сервіси | у образі їх немає (докладно — [GAPPS.md](GAPPS.md)): без microG не працюють push і вхід у застосунки, які на них тримаються |

І ще одне, уже виміряне цим проєктом: «старий телефон» — не про будь-який
апарат. Єдиний реальний пристрій, який ми дивилися вимірюванням, — Galaxy J5
(2017): 32-бітна ABI без `arm64`, ядро 3.18, API 28, заблокований
завантажувач. TesseraOS на нього не ставиться в принципі, і компіляція
«постаратися» тут не допоможє. Межу обґрунтовано в [REQUIREMENTS.md](REQUIREMENTS.md).
