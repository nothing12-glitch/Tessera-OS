# Архітектура TesseraOS

## Шарова модель

```
┌──────────────────────────────────────────────────────────┐
│  Користувач: застосунки (Play / F-Droid / власні)         │
├──────────────────────────────────────────────────────────┤
│  Tessera UI-шар   ← цей репозиторій                         │
│   • RRO-оверлеї: палітра, форми, типографіка, іконки      │
│   • System apps: Settings-шкіра, лаунчер, оновлення       │
│   • Конфіг продукту, branding, build-скрипти              │
├──────────────────────────────────────────────────────────┤
│  LineageOS 22.x  (Android 15, AOSP + their infra)         │
│   • framework, SurfaceFlinger, SystemUI, PackageManager    │
│   • OTA-інфра, privacy guard, root apps, backup            │
├──────────────────────────────────────────────────────────┤
│  Android Open Source Project                               │
│   • ART, Binder, Camera2, Media, Keystore, Material lib    │
├──────────────────────────────────────────────────────────┤
│  Ядро Linux + HAL + vendor-бібліотеки пристрою                  │
└──────────────────────────────────────────────────────────┘
```

Ми правимо тільки верхній шар. Це принципово:

- **Оверлеї замість форків.** RRO (Runtime Resource Overlay) підміняє значення
  ресурсів у `android`, `com.android.settings`, `com.android.systemui` без
  змін у коді AOSP. Наслідок: апстрім-зміни не конфліктують, тему можна
  вимкнути/перемкнути на льоту, а `repo sync` не ламається.
- **Конфіг продукту замість патчів.** `build/tessera.mk` лише успадковує
  конфіг бази й додає пакети/властивості.
- **Застосунки як окремі модулі.** Кожен own-app — самостійний Gradle-проєкт,
  що встановлюється в `system_ext/app` або `product/app`.

## Чому LineageOS, а не чистий AOSP

| | Чистий AOSP | LineageOS 22.x (наш вибір) |
|---|---|---|
| Прошивка на реальні пристрої | немає інструментів | є (updater, OTA) |
| Безпека/патчі | треба стежити самому | відстежує CVE-місяці |
| Device tree | немає жодного | сотні підтримуваних |
| Драйвери джерела/базу | емулятор і Pixel | широкий набір SoC |
| Стабільність релізу | experimental | підписані офіційні білди |
| Обсяг роботи на шляху «перший образ» | роки | тижні |

Чистий AOSP лишається валідною опцією для дослідницьких гілок:
`lunch aosp_x86_64-trunk_staging-userdebug` дає «голий» Android на емуляторі.
TesseraOS на цьому етапі його не обирає, бо користувачеві потрібна робоча
система з оновленнями.

## Каталоги

| Шлях | Призначення |
|---|---|
| `manifest/tessera.xml` | додаток до маніфеста бази: один проєкт + `linkfile` (кладуть `.repo/local_manifests/`) |
| `build/tessera.mk` | конфіг продукту `tessera_x86_64` (Make); успадковує платформу емулятора бази |
| `build/board/AndroidProducts.mk` | оголошення lunch-таргетів; разом з `.mk` вище лінкується в `device/tessera/x86_64/`. Власного `BoardConfig.mk` немає спеціально: платформу дає `device/generic/goldfish/board/emu64x` |
| `build/scripts/` | bootstrap, `new-tree.sh` (дерево бази + наш шар), збірка, пакування GApps, запуск AVD, підготовка APK наших застосунків (`prepare-app.sh` за реєстром `apps.list`), перевірки інтеграції й посилань збірки |
| `overlay/themes/` | RRO-пакети MD3 |
| `overlay-packages/` | build-time підміни файлів застосунків (сітка лаунчера 5×6) — не RRO, бо `res/xml` з атрибутами чужого namespace не лінкується оверлеєм |
| `config/gapps/` | профілі встановлення GApps/microG |
| `apps/launcher/` | власний лаунчер (Kotlin + Compose MD3): сітка 5×6, док 5, шухляда з пошуком, рядок «дата + погода». В образі — модуль `TesseraLauncher` |
| `apps/calculator/` | власний калькулятор: `BigDecimal`-арифметика, тональні клавіші MD3, науковий запис за межами `1E-10 … 1E21`. Модуль `TesseraCalculator` |
| `apps/files/` | власні «Файли» поверх SAF (без дозволу на все сховище): крихти, пошук, чотири порядки сортування, створення/перейменування/видалення. Модуль `TesseraFiles` |
| `apps/clock/` | власний годинник: три вкладки MD3 `NavigationBar` (секундомір, таймер, будильники), `setAlarmClock` з точним спрацюванням у Doze, пере-постановка після перезавантаження. Модуль `TesseraClock` |
| `apps/dialer/` | власний «Телефон»: набір номера, `InCallService` з вікном розмови поверх замка, журнал за днями й пошук (цифри працюють як T9). Модуль `TesseraDialer`; стоковий `Dialer` прибрано з переліку пакетів у `build/tessera.mk`, щоб `ROLE_DIALER` тримав лише один застосунок |
| `apps/messaging/` | власні «Повідомлення»: список розмов, нитка SMS, композер із кошторисом частин за GSM 23.038, пошук і `smsto:`. Модуль `TesseraMessaging`; стоковий `messaging` прибрано з переліку пакетів у `build/tessera.mk`, щоб `ROLE_SMS` тримав лише один застосунок. MMS свідомо немає — див. `apps/messaging/README.md` |
| `apps/camera/` | власна «Камера» на CameraX: фото, відео зі звуком, ліхтарик, зум жестом і редактор одного знімка (поворот, пропорція, яскравість, контраст). Модуль `TesseraCamera`; `overrides` немає свідомо — див. `apps/camera/Android.bp` |
| `.github/workflows/` | CI: оверлеї (hosted), наші застосунки — матриця по `apps.list` (hosted), установчий пакунок для VM у GitHub Release (`release.yml`), ROM (self-hosted) |

Усі сім застосунків збираються Gradle-ом окремо від дерева AOSP і входять в
образ як `android_app_import` (`apps/<застосунок>/Android.bp`): бінарників у
git немає, тому перед `m` скрипт кладе свіжий APK у `prebuilt/`. Реєстр
`build/scripts/apps.list` — єдине місце, де записано, які застосунки взагалі є;
його читають і `prepare-app.sh`, і `check-app-integration.sh`, і CI-матриця.

## Конвенції гілок і версій

- `main` — тільки те, що проходить CI; релізні теги `v15.<lineage>.<tessera>`.
- Версія product-властивості `ro.tessera.version` збігається з тегом.
- Зміни до `overlay/**` вимагають скріншота до/після в PR (див.
  [CONTRIBUTING.md](CONTRIBUTING.md)).

## Roadmap

1. **M0, каркас** — структура, CI на оверлеях, документація. *(готово)*
2. **M1, образ на емуляторі** — `tessera_x86_64` збирається, MD3-тема
   застосована static-overlay, microG за замовчуванням. *(поточний: усе це
   є в репо, бракує самого зібраного образу й знімків з екрана. Установчий
   пакунок для VM публікується як реліз — чинний `v15.22.2.2`; у `v15.22.2.0`
   теми не було через падіння збірки оверлеїв у CI, а в `v15.22.2.1` не
   вистачило «Камери».)*
3. **M2, UI-шар** — власні Settings-екран і лаунчер-концепт на Compose/MD3,
   динамічна палітра від шпалер. *частково: сім застосунків (лаунчер,
   калькулятор, «Файли», годинник, «Телефон», «Повідомлення», «Камера») вже в
   репо й збираються CI з тестами; лишилися Settings-шкіра й перевірка ролей
   на живому пристрої.*
4. **M3, пристрої** — перші 2–3 реальні телефони з підтримкою в LineageOS,
   own-app у `product`.
5. **M4, інфраструктура релізу** — підписані образи, OTA-сервер, публічний
   канал зворотного зв'язку, відтворювані збірки. *частково: пакунок APK
   для VM уже публікує `release.yml`; образи й OTA — попереду.*

## Припущення, які треба перевірити на своєму checkout

Назви ресурсів MD3 у framework змінюються між релізами Android, а імена
device-таргетів — між версіями LineageOS. Перед першим білдом звір:

- `lunch <target>` — перелік бере з `device/**/AndroidProducts.mk`
  (`PRODUCT_LIST`, `PRODUCT_MAKEFILES`); наш файл — `build/board/AndroidProducts.mk`;
- реальні імена токенів у
  `frameworks/base/core/res/res/values/colors_device_defaults.xml`;
- чи існує `lineage_x86_64` у твоїй гілці маніфесту (якщо ні — `aosp_x86_64`).
