# Tessera Welcome — майстер першого запуску

Це **не застосунок**. Іконки в шухляді в нього немає й бути не може: він
єдиний екран, який система показує один раз — поки пристрій не налаштовано.
Десять кроків: вітання, мова й регіон, доступність, вигляд, навігація, профіль
живлення, приватність мережі, обліковий запис, демо світлового краю, готово.
Kotlin + Compose Material 3, динамічна палітра (Monet) з fallback і ручний
акцентний колір.

Кроків саме десять, бо стільки є виборів, які справді хтось робить на першому
запуску; і кожен із них на екрані названий своїм словом — що саме сталося:
запис у систему, лише збереження в файл модуля чи відкритий чужий екран.

Різниця з «звичайним застосунком» — не в дизайні, а в кількох рядках коду,
які без прав рівня системи написати неможливо:

| що робить | чим це виправдане |
|---|---|
| пише `Settings.Global.device_provisioned` і `Settings.Secure.user_setup_complete` | `WRITE_SECURE_SETTINGS` (`signature\|privileged`) |
| перемикає тему всього телефону, а не свого вікна | той самий дозвіл і той самий рядок `ui_night_mode`, що й перемикач у Налаштуваннях |
| ставить масштаб шрифта для всього телефону | той самий дозвіл, рядок `Settings.Secure.font_scale` |
| з'являється саме на першому запуску і більше ніколи | фільтр `CATEGORY_SETUP_WIZARD` + `finish()`, коли система вже налаштована |

Тому модуль лежить у `system_ext/priv-app`, а не в `system_ext/app`, і має
дозвільний запис `privapp-permissions-tessera-welcome.xml`. Без нього образ із
`ro.control_privapp_permissions=enforce` (`build/tessera.mk` §5) не
завантажився б взагалі.

Це **перший** з двох власних застосунків, які повернулися в образ після
рішення «прибрати наші застосунки зовсім» (2026-10-25). Він винятковий тому,
що нічого не робить замість системи: домашній екран, телефон, повідомлення,
камера, годинник, калькулятор і «Файли» й далі дає база — див.
`build/tessera.mk` §2b. Другий виняток — `apps/halo`, світловий край.

У git немає жодного бінарника: ні `gradle-wrapper.jar`, ні APK. Знак на
логотипі — та сама геометрія, що й у `brand/android/tessera_mark.xml`.

## Архітектура

* `logic/WelcomeFlow.kt` — чистий Kotlin без `android.*`-імпорту: перелік
  кроків, «Далі»/«Назад»/«Пропустити», крапки прогресу і реєстр системних
  записів. Кожен крок знає про себе дві речі: `skippable` (чи тут справді є
  що пропускати — на перших кроках і на «Готово» немає) і `writes` (чи цей
  крок пише в систему). Стан запису — один з трьох: `NOT_ATTEMPTED`, `APPLIED`,
  `BLOCKED` — і до спроби він завжди `NOT_ATTEMPTED`, тож жоден крок не встигає
  пообіцяти успіх.
* `logic/WelcomeChoices.kt` — усі вибори користувача (тема, акцент, мова,
  регіон, масштаб шрифта, навігація, профіль живлення, політика MAC) і
  колірна математика для акцента: яскравість за Rec. 709, контрастний текст,
  підсвічування темного акцента на темному тлі. Зовнішні значення
  (`UiModeManager`, рядки `Settings`) підставляє Android-шар — тут лише мапічі.
* `logic/WelcomeMotion.kt` — рух у числах: довжина вітання (рівно 3000 мс),
  межі появи кожного елемента, цикл демо краю. «Анімація триває три секунди»
  перевіряється тестом, а не на око.
* `data/SystemFlags.kt` — єдине місце, де торкаються системних прапорців:
  `isProvisioned()`, `nightMode()`, `setNightMode()`, `fontScale()`,
  `setFontScale()`, `markProvisionedSafely()`. Останнє повертає `false` замість
  того, щоб зробити вигляд, що вийшло.
* `data/ModulePrefs.kt` — файл модуля `tessera_welcome`. Тільки те, чого
  `WRITE_SECURE_SETTINGS` не покриває: мова, регіон, акцент, навігація,
  профіль живлення, політика MAC, високий контраст. «Проходив чи ні майстер»
  тут не зберігається — див. нижче.
* `data/CompletionCue.kt` — звук і вібрація на завершення: `ToneGenerator`
  (без дозволів) + `VibratorManager` (дозвіл `VIBRATE`, звичайний).
* `WelcomeViewModel` — пошук пакунка `com.google.android.gms`, два
  `startActivity` (акаунт і системний екран), виклики `SystemFlags` і
  `ModulePrefs`, спроба запису з чесним результатом.
* `ui/` — `TesseraWelcomeTheme` (Monet + edge-to-edge + ручний акцент) і
  `WelcomeScreen` (один `AnimatedContent` на всі переходи, `StepDots` замість
  «Крок N із M», крапки для пропущених кроків).

Уся логіка вище з `logic/` покривається юніт-тестами на JVM
(`app/src/test/kotlin/os/tessera/welcome/logic/`) — саме тому порядок кроків
живе там, а не в UI.

Власний файл налаштувань у модуля знову є, але він нічого не підміняє: там
лежать лише наміри («обрав таке»), а не факти про систему. Єдиний критерій,
показувати майстер чи ні, лишився один і той самий — системний
`device_provisioned`. Поки вітальня була звичайним застосунком, «пройдено»
доводилось ховати у власному файлі, і саме це було підміною: система про той
файл не знала.

### Прогін B — 2026-10-26, той самий модуль уже з `priv-app`

AVD `TesseraUD` на образі `android-35/google_apis/x86_64` (`userdebug`,
`ro.control_privapp_permissions=enforce`). APK лежить у
`/system_ext/priv-app/TesseraWelcome/`, дозвіл — у
`/system_ext/etc/permissions/privapp-permissions-tessera-welcome.xml`. **Жодного
`adb install` у цьому прогоні не було взагалі** — і саме тому він щось доводить.

| перевірка | результат (знімок термінального виводу) |
|---|---|
| чи система вважає модуль системним | `pm path` → `package:/system_ext/priv-app/TesseraWelcome/TesseraWelcome.apk`; `dumpsys package` → `codePath=/system_ext/priv-app/TesseraWelcome`, `flags=[ SYSTEM DEBUGGABLE HAS_CODE … ]` |
| чи дозвіл видано сукупністю «priv-app + allowlist» | `android.permission.WRITE_SECURE_SETTINGS: granted=true` і `android.permission.MODIFY_DAY_NIGHT_MODE: granted=true` після ребута, без `adb install -g` |
| чи `enforce`-політика не вбиває завантаження | `init: Overriding previous property 'ro.control_privapp_permissions':'disable' with new value 'enforce'`, `sys.boot_completed=1`, PackageManager логує `/system_ext/priv-app/TesseraWelcome changed; collecting certs` |
| десять кроків з partition-встановленого модуля | так; крім того `font_scale`: `null → 1.4` і `ui_night_mode`: `null → 2` від тапів на кроках 3 і 4 |
| тема застосовується наживо, а не після ребута | тап «Темна»: `secure=2 · mNightMode=2 (yes) · mCurUiMode=0x21` у ту ж секунду і на +1/+4 с; зворот «Світла» → `0x11`. Знімок лаунчера: пігулка пошуку біла → темно-сіра, тобто перемальовується не наше вікно |
| два майстри в образі | `E PackageManager: There should probably be exactly one setup wizard; found 2: matches=[os.tessera.welcome/.WelcomeActivity p=1000 m=0x108000, com.google.android.googlesdksetup/.DefaultActivity p=3 m=0x108000]` — наш має вищий `priority`, і це єдине виміряне порівняння |

**2026-10-27 той самий прогін став відтворюваним.** Вище — знімок чужого
термінального виводу, і саме тому його не стільки перевірено, скільки переказано.
Тепер ті ж п'ять тверджень вимірює `bash build/scripts/check-welcome-live.sh
install <apk>`: partition, `codePath`, прапор `SYSTEM`, обидва дозволи
`granted=true` — і жодного `adb install` у прогоні. На свішому пакунку
(`.scratch/apks-welcome3`, зібраному з маніфеста, який скрипт друкує перед
збіркою) — **5 із 5**, і одразу після нього `theme` — **9 із 9**, а `walk
--fresh` — **4 із 4**. Рядок стану після того проходу: `device_provisioned=1`,
`user_setup_complete=1`, `font_scale=1.4`, `ui_night_mode=1`. На кроці 4 той
прохід нічого не обирав — він іде «Далі» всі десять кроків, тому тема лишилася
на дефолті (світла), і крок 10 чесно друкує «Тема — Світла». Три прогони поспіль
на одному partition-встановленому модулі — тобто й десять кроків, і тема, і
запис у `secure` більше не залежать від того, чи хтось видав дозвіл руками.

Дві спроби перед вдалою провалилися чесним чином, і обидві причини — не образу:
старий APK (збірка 18:19 проти маніфеста 20:37 ⇒ `MODIFY_DAY_NIGHT_MODE` у
пакунка просто не було) і 80 МБ `/mnt/scratch`, з якого f2fs повертає місце лише
після ребута. Обидві записані як пастки №8 і №9 у `docs/EMULATOR.md`.


### Чотири дефекти, які знайшов саме живий прогін

Перші три не видно в коді й не ловиться жодним із 36 тестів — усі три помітні
лише на відрендереному екрані. Четвертий не побачив би й екран: він виглядав би
правильно в нашому вікні й неправильно на решті телефона.

1. **Markdown у рядках інтерфейсу.** На кроках «Вигляд», «Профіль живлення» і
   «Приватність мережі» на склі лишалися бектики: «а це не рядок
   \`WRITE_SECURE_SETTINGS\`». Бектик — конвенція README, а не типографіка
   Android. Прибрано з трьох рядків, і в `build/scripts/check-app-integration.sh`
   додано перевірку №14: `grep` бектика всередині `<string>` тепер валить
   збірку до того, як хтось побачить такий екран. Перевірку перевірено:
   підкинутий рядок із бектиком у `apps/halo/.../strings.xml` справді дав
   `Провалено`.
2. **Кружечок «Як шпалера (Monet)» фарбувався в `colorScheme.primary`.**
   Тобто щойно людина обирала фіксований акцент, перший кружечок ставав його
   копією — вибір «колір дає система» виглядав як ще один такий самий синій.
   Тепер це градієнт із чотирьох сидів уже існуючої палітри (`INDIGO`, `SKY`,
   `VERDIGRIS`, `AMBER`): він не заявляє одного кольору, бо й не має одного.
3. **Notice «ще не записували» суперечив видимому.** Стан запису живе в
   памʼяті процесу, а чіпи тема й масштаб читають справжнє системне значення.
   Тому після повторного запуску майстра екран показував вибрану світлу тему і
   водночас «Тему ще не записували». Виправлено формулювання на «Цього запуску
   тему ще не записували» — це дослівно правда. Не зроблено свідомо: не
   підміняти цей стан позначкою «записано», бо для цього довелося б зберігати
   власний прапорець «ми колись успішно записали», а він переживе скидання
   системного перемикача й збрехати може вже в бік успіху.
4. **Запис у `Secure` ≠ застосована тема.** Це єдиний дефект, який видав себе
   лише в прогоні B, і він робив правдою наполовину головну обіцянку крока.
   Виміряно на `TesseraUD`: сирий `Settings.Secure.putInt("ui_night_mode", 2)`
   пише рядок (`settings get secure ui_night_mode` → `2`), виклик не падає, а
   `dumpsys uimode` лишається на `mNightMode=1 (no)` / `mCurUiMode=0x11` —
   телефон НЕ темніє; новий режим зʼявляється лише після перезавантаження. Тож
   «Застосовано до всієї системи» у момент тапу було брехнею, перевірити яку
   читанням бази неможливо: база якраз «відповідає правильно».

   Виправлення у три ходи: пише тепер `UiModeManager.setNightMode()` (сервіс
   застосовує режим наживо); стан «застосовано» вирішує не відсутність винятку, а
   `appliedNightMode() == mode` — синхронне читання режиму з того ж сервісу
   (не `resources.configuration`: конфігурація доходить асинхронно й давала б
   хибний `BLOCKED`); і — те, без чого перші два ходи не працювали б узагалі —
   `system_server` відкидав виклик мовчки:
   `E/UiModeManager: Night mode locked, requires MODIFY_DAY_NIGHT_MODE
   permission`. Дозвіл `signature|privileged`, тому він тепер і в маніфесті, і
   в дозвільному списку. Після цього тап «Темна» дає `mCurUiMode=0x21` у ту ж
   секунду, а зворот «Світла» — `0x11`; на знімку лаунчера його біла пігулка
   пошуку стає темно-сірою, тобто перемальовується не наше вікно.

   Два факти, які не влізли б у цю історію, якби ми їх не виміряли:

   - **Блокування знімає дозвіл, а не налаштованість.** `mNightModeLocked=true`
     на цьому образі не зникає навіть тоді, коли `device_provisioned=1` — тобто
     «ми ж у OOBE, тому й не вийшло» було б поясненням убік.
   - **Застосоване наживо не обовʼязково переживає ребут.** Після тапу
     «Темна»: `secure=2 · mNightMode=2 (yes) · 0x21`. Після перезавантаження:
     `secure=2`, але `mNightMode=1 (no) · 0x11` і `cmd uimode night` → `no`.
     Рядок лишається, режим сервіс бере власний. Чому — не читали
     (`frameworks/base` не синхронізовано), тому крок 4 каже «застосовано», а не
     «застосовано назавжди», і жодна документація модуля не обіцяє, що тема
     вернеться після ребута.

### Чого досі не доведено

- **Система сама нас не кликала — причину названо 26.10.2026.** Усі проходи йшли
  з явним `cmp=`. Три чисті завантаження з `device_provisioned=0` на `TesseraUD`
  лишили фокус на лаунчері, `dumpsys window` нашого вікна не показав, а
  `persist.log.tag.ProvisionController = VERBOSE` на 29 780 рядків журналу не дало
  **жодного** рядка теги. Пояснення тепер виміряне, а не здогадане:
  у Android 15 перший екран дістається тому, хто оголошений `CATEGORY_HOME`, а не
  `CATEGORY_SETUP_WIZARD`. Два свіжі boot-буфери (21 506 і 28 085 рядків) мають
  **0** рядків `SETUP_WIZARD`; `dumpsys package` дає `Setup Wizard: none`;
  `cmd package query-receivers -a android.intent.action.USER_UNLOCKED` —
  `No receivers found`; на образі немає `com.android.provision`, а
  `ro.setupwizard.mode` не заданий. Доказ і три правки, які це закривають, —
  `docs/FEASIBILITY.md` §6.
- **Неявний виклик не резолвиться, і це не наш дефект.** `am start -a MAIN
  -c SETUP_WIZARD` без `-n` дає `unable to resolve Intent` — і так само не
  резолвиться комітний `com.google.android.googlesdksetup/.DefaultActivity`,
  навіть від uid 0. Наш фільтр у своїх межах правильний: `resolve-activity` бачить
  `os.tessera.welcome/.WelcomeActivity`, `priority=1000`, `exported=true`,
  `enabled=0`. Додавання `CATEGORY_DEFAULT` до запиту, навпаки, ламає резолвінг
  (`No activity found`), тож вписувати `DEFAULT` у поточний однокатегорійний
  фільтр «на всяк випадок» не можна.
- **`priority="1000"` нічого не виграє — обидві гіпотези закриті виміром.**
  «Заважав другий мастер» не пояснює нічого: з вимкненим
  `com.google.android.googlesdksetup` фокус лишився тим самим, кеш — `none`, а
  рядок `found 2` PackageManager друкував і далі, бо його скан-тайм запит не
  зважає на вимкнений стан. Гіпотеза про `config_deviceProvisioningActivity`
  теж закрита: рядка на теґу бази (`android-15.0.0_r32`) немає взагалі. Вирішує
  роль, а не `priority`: `dumpsys role` віддає `ROLE_HOME` лаунчеру, і
  `resolve-activity MAIN + HOME + DEFAULT` повертає його з `isDefault=true` —
  match-прапорці `0x200`, `0x80000`, `0x80200` цього не змінюють.
- **Після «Увійти в Tessera» фокус пішов не на лаунчер, а на вікно, яке
  лишалося знизу** (того дня там стояв екран налаштувань Halo). Майстер просто
  викликає `finish()` — це правильно для `priv-app`, де система тримає
  домашній екран під майстром, але на виклику з shell ця перевірка неробоча.
  Раніше той самий рядок таблиці стверджував `NexusLauncherActivity` — він
  описував влучний збіг, а не поведінку модуля.
- **Звук і вібрація на «Готово»** — на образі без мотора вони непомітні; що не
  падають — підтверджено лише тим, що прохід дійшов до кінця.
- **Повільний пристрій.** Демо краю й анімації дивилися на x86_64-емуляторі без
  навантаження; «не лишає залиплого кадру на слабкому залізі» лишається
  неперевіреним.

### Пастка, на якій ловиться кожен, хто це повторює

`adb remount` на емуляторі тримає зміни в оверлеї на розділі `/mnt/scratch` —
той на цьому образі має **80 МБ**. Наш debug-APK — 24 МБ, тож другий запис
поверх існуючого іноді завершується з `ENOSPC`, який `adb push` не показує:
«1 file pushed», а файл зникає за секунду. Два рази це виглядало як «модуль
зламалося», хоча ламалося лише завантаження. Тому скрипт перевірки тепер
робить `df`-подібний тест перед `push` (`overlay on /system_ext … (rw`) і
`ls` після нього, а не віриться коду виходу adb.


## Чого цей модуль НЕ робить

Список навмисно довгий: помилка «модуль є в образі, а обіцянки з нього
виправдані» — той самий клас, від якого захищає `check-app-integration.sh`.

**Не перекриває майстра бази.** Механізм бази вже звірено з кодом на теґу
`android-15.0.0_r32`: `packages/apps/Provision` тримає `HOME + DEFAULT +
SETUP_WIZARD` із `priority="1"` і сам вимикає свій компонент після запису
прапорців. Наш маніфест досі лише `MAIN + SETUP_WIZARD`, тому перший екран нам
не дістається — деталі в `docs/FEASIBILITY.md` §6. Перехід на `HOME` змінює
поведінку кнопки «додому» під час майстра, тому правку не вносимо мовчки:
спершу живий прогін на образі з вільною роллю `ROLE_HOME`, потім рішення.

**Не показує ані слова, якщо система вже налаштована.** Це не «закривається
помилково»: `skipWhenAlreadyPassed()` читає `device_provisioned`, і поки він
рівний 1, модуль не має права перекривати екран.

**Не пише прапорці мовчки.** Якщо дозволу раптом немає, на екрані з'являється
`welcome_theme_not_applied` / `welcome_write_blocked` /
`welcome_provision_failed` — прямий текст про те, що саме не вийшло. Ховати це
за кнопкою, яка «ніби спрацювала», — той самий клас брехні, від якого захищає
цей README. Для теми стан «застосовано» вирішує не відсутність винятку, а
прочитаний у `UiModeManager` режим: саме через такий оракул живий прогін і
показав, що винятку немає, а теми — немає.

**Не обіцяє Google-сервісів.** У образі їх немає: `build/tessera.mk` §3
свідомо тримає `PRODUCT_PACKAGES` без GApps і без microG, а
`.github/workflows/policy.yml` блокує власницькі бінарники. Кроку з обліковим
записом вистачає чесного факту: якщо на пристрої є постачальник `GmsCore-API` —
показуємо кнопку «Додати акаунт», якщо немає — кажемо, що додавати нікуди, і
пропонуємо пропустити.

**Не робить того, чого не може OOBE взагалі.** SIM і відновлення з резервної
копії на цих кроках немає: вони потребують дозволів рівня оператора/мережі й
системних сервісів. Мову не перемкнуто, і причина саме в дозволі:
`CHANGE_CONFIGURATION` у модуля немає, тому крок зберігає вибір і веде на
системний екран мови.

**А навігація, живлення й MAC — це рішення, а не межа.** На відміну від мови,
тут модуль уже тримає потрібний дозвіл: 27.10.2026 на `userdebug`-образі
`WRITE_SECURE_SETTINGS` видано з allowlist (прогін `install` — 5/5), ключ
`settings get secure navigation_mode` живе в образі й повертає `2` — значення
саме системи, наш модуль його не писав. А запис такого класу в цьому ж образі
уже реально виконується: крок 4 пише `ui_night_mode`, і прогін `theme` (9/9)
бачить, як значення переходить `1 → 2` у ту ж секунду, коли тапнуто «Темна».
Тобто ці три кроки вперлися не в межу дозволу — вони лиш зберігають вибір і
кажуть, де його застосувати, бо так вирішено свідомо. Це не «не можу», а «не
роблю», і воно тримається до слова власника проєкту: або застосовувати наживо
так само, як тема, або й надалі лише питати.

**Як це не розмиється.** Від 27.10.2026 такі речення звіряє CI:
`build/scripts/check-doc-claims.sh` читає маніфест і дозвільний список і валить
прогін, якщо документ твердить «`X` у модуля немає», а `X` оголошений, — або
навпаки: твердить «`X` видано з allowlist», а запису в allowlist немає. У нього
є власний `--selftest` на свідомій брехні, бо перевірка, яка не вміє падати,
нічого не перевіряє. Межа теж чесна: речення без імені дозволу — «те саме з
навігацією, живленням і політикою MAC» — скрипт не бачить узагалі. Саме тому в
абзацах вище ім'я дозволу стояло в кожному твердженні, а не лише в заголовку
таблиці.

Той самий огріх жив і в рядку інтерфейсу крока 5: «навігацію перемикають
налаштування бази (оверлей конфігурації навігації), а не рядок, який покриває
наш дозвіл» — теж твердження про межу, якої в образі немає. Прибрано 27.10.2026,
і рядок тепер каже лише те, що справді робить модуль: зберігає вибір. Два інші
кроки лишалися чесними: живлення й MAC спираються на системні сервіси
(`PowerManager` і конфіг мережі в `WifiManager`), а не на запис у `secure`, тому
в їхніх рядках немає імен дозволів — просто «дозволів рівня системи, яких у
цього модуля немає», і це правда без вгадування назв.

Через це кроків десять, а не двадцять: стільки виборів справді робить людина
на першому запуску. І кожен крок каже правду про те, що з його вибором сталося
далі — запис у систему, збереження в файл модуля чи відкритий чужий екран.

## Збірка й установка

```bash
# у WSL-хості (Gradle 8.14.3 + Android SDK), див. docs/BUILD.md
cd apps/welcome
gradle --no-daemon :app:assembleDebug :app:testDebugUnitTest
# APK → app/build/outputs/apk/debug/app-debug.apk
```

На пісочничному образі `user` (так само, як перевіряли 2026-10-25). Цей блок —
**скидання майстра для тестів**, і більше ні для чого: у справжнього користувача
пристрій налаштовується один раз, і жодної кнопки «скинути» в модуля немає.

```bash
adb install -r -g app/build/outputs/apk/debug/app-debug.apk   # -g — щоб дозвіл видано було як виняток
adb shell settings put global device_provisioned 0            # «телефон щойно з коробки»
adb shell settings put secure user_setup_complete 0
adb shell am start -a android.intent.action.MAIN \
  -c android.intent.category.SETUP_WIZARD os.tessera.welcome/.WelcomeActivity
# темна тема для публічних знімків:
adb shell cmd uimode night yes
```

Майте на увазі: після «Увійти в Tessera» прапорці піднімуться справді, і
наступний запуск уже нічого не покаже — саме це ми й перевіряли. Показувати
майстер чи ні вирішує лише `device_provisioned`: власного запису «пройдено» в
`tessera_welcome` (файл `ModulePrefs`) немає, там лежать лише наміри користувача.

У образ модуль іде двома рядками, які перевіряються статично:
`build/scripts/apps.list` (`welcome|TesseraWelcome|os.tessera.welcome|…`) і
`PRODUCT_PACKAGES += TesseraWelcome` у `build/tessera.mk`. `Android.bp` —
`android_app_import` з `presigned: true`, `privileged: true` і
`system_ext_specific: true`, плюс `prebuilt_etc` із дозвільним списком.

Те, що в APK є `SETUP_WIZARD` і немає `LAUNCHER`, вирішує не кожен скрипт
окремо: правило живе в одному файлі `build/scripts/check-apk-manifest.sh`, а
кликать його і `prepare-app.sh`, і job `apk` у `build-apps.yml`. Раніше копія
правила жила в workflow окремо — і саме через це job «apk (welcome, …,
SETUP_WIZARD)» впав на першому ж білді після перетворення вітальні на мастер:
workflow у кожного APK все ще вимагав іконку (виправлено в `ad786c9`).

Окремо, щоб не плутали: `privileged` ≠ підпис платформним ключем. Привілей
дає partition і рядок у дозвільному списку; ключ платформи тут ні при чому, і
він нам не потрібен — тому модулю `presigned` і вистачає.

Живі перевірки цього шару автоматизує `build/scripts/check-welcome-live.sh`:
`install` (push APK і дозвільного списка в `system_ext`, права 755/644,
`restorecon`, ребут, другий remount і доказ `granted=true` без жодного
`adb install`), `theme` (крок 4: `mCurUiMode` 0x11 → 0x21 без перезавантаження,
потім поворот назад), `walk --fresh` (усі десять кроків тапами по `bounds` із
`uiautomator dump`) і `screens <dark|light>` (кадри всіх десяти кроків в одній
темі; з `--video` той самий прохід ще й записується `screenrecord`-ом на
пристрої й стягується як `out/welcome-live/<тема>/oobe-<тема>.mp4`). `--fresh`
стосується лише `walk`: він свідомо відновлюється на кроці зупинки, і без
чистого стану «1…10» не виміряти. `theme` і `screens` чистять стан модуля
примусово — їм потрібен конкретний крок (4 і 1), а не доказ відновлення; з
піднятим `device_provisioned` майстер виходить одразу, ще не показавши жодного
екрана, а після `screens`-проходу він лишається на кроці 10. Доведений порядок
і дев'ять пасток — readonly-оверлей
після кожного ребута, мовчазний ENOSPC на `/mnt/scratch`, підрядковий пошук вузла
в дампі (перший тап влучив у текст підказки замість кнопки), «живий adb» ≠
«готовий екран» на холодному boot, порожній дамп через уже відпрацьованого
майстра, мікс adb 1.0.39 із `PATH` проти 1.0.41, зупинка запису саме SIGINT
(інакше mp4 лишається без `moov`-атома, а розмір про те не каже), APK старший за
маніфест і `rm` в оверлеї, який повертає місце лише після ребута — в
`docs/EMULATOR.md`, розділ «Модуль у `system_ext/priv-app`: як це повторюється».

```bash
# APK збирається окремим кроком (блок вище); скрипт лише кладе його в образ і вимірює
bash build/scripts/check-welcome-live.sh install app/build/outputs/apk/debug/app-debug.apk
bash build/scripts/check-welcome-live.sh theme
bash build/scripts/check-welcome-live.sh walk --fresh
# кадри всіх десяти кроків в одній темі → out/welcome-live/<тема>/stepN.png
# (--fresh тут уже не потрібен: `screens` чистить стан сам; лишився в прикладах,
#  бо саме так виглядає виміряний прогін 26–27.10.2026)
bash build/scripts/check-welcome-live.sh screens dark
bash build/scripts/check-welcome-live.sh screens light --fresh
# + відео того ж проходу → out/welcome-live/dark/oobe-dark.mp4 (4.4 МБ, 105 с;
#   для сайту той самий запис стискається окремо: 2,5× швидше, 540×1200, 369 КБ)
bash build/scripts/check-welcome-live.sh screens dark --fresh --video
# -s <серіал пристрою> для будь-якої підкоманди; ADB=/шлях/до/adb — якщо adb не в PATH
# або якщо в PATH стоїть інша версія adb: мікс 1.0.39 із 1.0.41 ламає сервер посеред прогону
```
