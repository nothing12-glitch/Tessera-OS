# Tessera Halo — світловий край екрана

Концепт прийшов із новин 2026 року про **Pixel Glow**: у Android 17 Google
показує функцію, де телефон «світить» на сповіщення, батарею та ліхтарик —
фізично, діодами під задньою панеллю Pixel 11. У LineageOS 22.2 (і в
більшості телефонів) апаратного індикатора немає взагалі, а програмного
замінника база не дає: `Settings → Сповіщення → Індикатор` існує лише тоді,
коли залізо вміє діод.

Tessera Halo — те саме призначення, реалізоване на склі: широка м'яка смуга
світла по периметру екрана (~12 мм, без чіткої межі), забарвлена в колір
застосунку, що надіслав сповіщення; бірюзовий — резерв, коли кольору немає.

## Як це влаштоване

| частина | роль | чому саме так |
|---|---|---|
| `HaloListenerService` | джерело подій (`onNotificationPosted`/`onNotificationRemoved`) + стан DND (`currentInterruptionFilter`) | `NotificationListenerService` система тримає живим сама, тому власний foreground-сервіс не потрібен; DND читається без `ACCESS_NOTIFICATION_POLICY` |
| `HaloOverlay` | вікно `TYPE_APPLICATION_OVERLAY` на весь екран | вікно створюється **тільки на час світла** і прибирається по завершенні імпульсу |
| `HaloGlowSurface` | `SurfaceView`: малює три розмиті прошарки смуги окремим поверхневим рендером | поверхня дає справжнє розмиття (`BlurMaskFilter`) без чіткої межі; кади рахує чиста логіка, а не `View` |
| `HaloTileService` | плитка Quick Settings | другий, поряд із перемикачем, спосіб увімкнути/вимкнути край; показує актуальний стан |
| `logic/HaloPlan` | чи світити, з якою яскравістю, який колір | чисті правила, накриті юніт-тестами |
| `logic/HaloMotion` | криві анімації | те саме число живе й у превʼю на екрані |
| `logic/ColorBloom` | домінантний колір із пікселів + компенсація зрізу альфи | математика без Android-класів → тестується на JVM |
| `HaloSettingsActivity` | налаштування, дозволи, тест | жодного рішення про світло без перечитаних дозволів |

Візерунки: **Хвиля** (дві смуги біжать периметром, `DashPathEffect` з
анімованою фазою), **Пульс** (край дихає), **Суцільно** (рівне світло). Їх
рівно три — редактора сцен навмисно немає. Імпульс триває 3 с
(`HaloConfig.IMPULSE_MS`).

## Що перевірено наживо

Прогін 2026-10-26 на емуляторі `android-37.0/google_apis_playstore/x86_64`
(`ro.build.type=user`, API 37, 1080×2400 @420 dpi, темна тема). Це чужий
стоковий образ, а не наш: він доводить поведінку поверхні та слухача, але не
те, як край виглядає на нашій збірці.

Метод вимірювання, а не «на око»: `screenrecord` 6 с на час імпульсу, далі
`ffmpeg -vf fps=6` і `signalstats` — середня яскравість смуги 70 px вздовж
лівого краю (`crop=70:ih:0:(ih/2-70)`), кадр за кадром. Фон того місця на
шпалерах — 85,5; все, що вище, є світлом краю. Кадрів і лог — у
`.scratch/halo-live/`, вони не в git.

| кейс | як створено умову | пік YAVG | висновок |
|---|---|---|---|
| край горить | типовий стан, DND вимкнено, 100 % | 126,9 | +41 над фоном — SurfaceView у overlay-вікні реально композитується і потрапляє у знімок |
| DND | `cmd notification set_dnd none`; перевірено `mInterruptionFilter=3`, `mZenMode=ZEN_MODE_NO_INTERRUPTIONS` | 85,7 | +0,2 — край не горить; `onInterruptionFilterChanged` ловиться |
| батарея 5 % | `dumpsys battery unplug; dumpsys battery set level 5` (пристрій показав `level: 5`) | 85,7 | +0,2 — поріг 20 % тримає, світло вимкнено |
| батарея 50 % | те саме, `level 50` | 124,3 | +38,8 |
| батарея 100 % | `level 100` | 138,9 | +53,4; відношення 38,8 : 53,4 = **0,73** проти передбаченого множника `batteryFactor(50) = 0,75` — затемнення за зарядом працює так, як порахували |
| локскрін | PIN + `KEYCODE_SLEEP` + `KEYCODE_WAKEUP`; `isKeyguardShowing=true`, фокус — `NotificationShade` | 69,1 | +0,1 від фону 68,9 (темніше скло) — на заблокованому екрані краю немає |

З того ж `logcat` — дві поведінки платформи, які ми закладаємо в малюнок:

```
W/WindowManager: App os.tessera.halo has a system alert window (type = 2038)
                 with FLAG_NOT_TOUCHABLE and LayoutParams.alpha = 1.00 > 0.80,
                 setting alpha to 0.80 ...
D/WindowManager: setClientSurface Surface(name=VRI-#434)/@0xb782d0e for
                 12666c2 os.tessera.halo
```

Тобто стеля `alpha` = 0.80 підтверджена на живому образі (компенсація в
премультипованому малюнку — не вигадка), і поверхня `SurfaceView` отримує
власний `ClientSurface`.

### Три речі, які цей прогін відкрив про shell — і які ми більше не обіцяємо

- `settings put secure enabled_notification_listeners …` на цьому образі **не
  тримається**: значення повертається до попереднього. Працює інший шлях —
  `cmd notification allow_listener os.tessera.halo/.HaloListenerService`, після
  нього слухач справжній. Для користувача це нічого не змінює (доступ усе одно
  видає людина), але збиває з пантелику будь-який авто-тест, який намагався
  увімкнути слухача через `settings`.
- `settings put secure sysui_qs_tiles …` перезаписується **миттєво**: навіть
  читання одразу після запису віддає старий список. Плитку Quick Settings
  неможливо покласти заздалегідь — ані скриптом, ані образом. Її додає лише
  людина в редакторі панелі; саме тому в застосунку є другий перемикач, а
  плитка — лише зручність, а не обовʼязковий шлях.
- У `cmd notification post` немає прапорця пріоритету (`-P` не існує), тому
  тестове сповіщення завжди має `priority=0`. Фільтр «лише помітні»
  (`PRIORITY_LOUD = 0`) пропускає його якраз межею, тож цей спосіб не
  перевіряє, що *низький* пріоритет край справді ігнорує.

### Два дефекти інтерфейсу, які знайшов саме живий кадр

Обидва виправлено того ж дня, і обидва було непомітні в коді:

- Заголовок «Візерунок» стояв у іншій типографіці, ніж сусідні розділи
  («ВИГЛЯД», «КОЛИ СВІТИТИ») — тепер той самий `SectionTitle`.
- Превʼю візерунка малювало штрих товщиною `band` по контуру, відступленому
  лише на `0,35 · band`, тож зовнішній прошарок обрізався краєм полотна й
  замість рамки було видно дві дуги по боках. Відступ тепер `0,6 · band`,
  смуга в превʼю — тонша.

## Чого цей застосунок НЕ робить

Це той розділ, який робить функцію чесною. Усе перелічене нижче — не «поки
не встигли», а межа того, що дозволяє публічний API без системного ключа:

- **не світиться, коли екран вимкнений або заблокований.** Вікно overlay
  система показує лише на розблокованому ввімкненому дисплеї; стан читаємо з
  `PowerManager.isInteractive` і `KeyguardManager.isKeyguardLocked` — без
  дозволів. Справжній AOD — окрема апаратна здатність.
- **не має діода й не імітує задню панель.** Це світло на склі, а не
  випромінювання ззаду телефону — на відміну від справжнього Pixel Glow.
- **не перемикає «Не турбувати» й не змінює гучність.** Під DND край
  вимикається повністю; стан беремо зі слухача (`currentInterruptionFilter` /
  `onInterruptionFilterChanged`) — це дає висновок без
  `ACCESS_NOTIFICATION_POLICY`.
- **не світить на вхідний дзвінок.** Край — про сповіщення, а не про
  розмови. Дзвінок упізнаємо зі `AudioManager.mode` (публічний стан), тому
  `READ_PHONE_STATE` нам не потрібен.
- **не є індикатором мікрофона.** Про мікрофон край не світить:
  консультативний індикатор приватності — справа системи, ми її не дублюємо.
- **не світить, коли батарея нижча за 20 %, і тьмяніє зі зниженням заряду.**
  Рівень і зарядку беремо зі sticky-інтента `ACTION_BATTERY_CHANGED` — без
  дозволу. Яскравість краю — це власна інтенсивність малюнка, а не системна
  яскравість екрана, тому `WRITE_SETTINGS` не потрібен.
- **не читає текст сповіщень.** З обʼєкта беруться package, пріоритет,
  категорія, flags і колір; сам `extras` з текстом не зачіпається й нікуди не
  надсилається.
- **не знає важливості каналу чужого застосунку.** `NotificationChannel`
  привʼязаний до пакета, тому замість нього — `notification.priority`. Через
  це «лише помітні» іноді не світиться на те, що система все одно показала б
  heads-up.
- **не світить без двох дозволів.** `SYSTEM_ALERT_WINDOW` і доступ до
  сповіщень видає лише людина в Налаштуваннях; без них застосунок не робить
  нічого й чесно пише про це на своєму екрані.
- **не є системним майстром і нічого не замінює.** Це одне вікно-оверлей над
  екраном на 3 секунди світла, а не сервіс рівня `signature|privileged`:
  модуль `presigned`, платформного ключа немає.

## Інтеграція в образ

Рядок `halo|TesseraHalo|os.tessera.halo|tessera-halo-debug|-` у
`build/scripts/apps.list` + `PRODUCT_PACKAGES += TesseraHalo` у
`build/tessera.mk`. Обидва кроки статично звіряє
`build/scripts/check-app-integration.sh`; `Android.bp` — `android_app_import`
з `presigned: true`, тому apk у git не лежить (політика `policy.yml`).

Останній стовпчик реєстру — прочерк: Halo не потребує категорії на кшталт
`HOME` чи `SETUP_WIZARD`. Його «категорія» — це дві ролі в Налаштуваннях. Від
27.10 їх наявність тримає статика: той самий `check-app-integration.sh` падає,
якщо з маніфеста зник `SYSTEM_ALERT_WINDOW`, звʼязка слухача
`BIND_NOTIFICATION_LISTENER_SERVICE` з фільтром `NotificationListenerService`
або плитка `BIND_QUICK_SETTINGS_TILE` — бо без будь-якого з цих трьох модуль
збирається, ставиться і мовчки не світить. Наживо від того лишається
саме поведінка: чи система привʼязує сервіс і чи край зʼявляється на склі.

## Збірка й установка

```bash
# на білд-хості (WSL2/Ubuntu):
cd apps/halo && gradle :app:assembleDebug :app:testDebugUnitTest

# на пристрій:
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell pm grant os.tessera.halo android.permission.POST_NOTIFICATIONS
adb shell appops set os.tessera.halo SYSTEM_ALERT_WINDOW allow
adb shell cmd notification allow_listener os.tessera.halo/os.tessera.halo.HaloListenerService
adb shell am start -n os.tessera.halo/.HaloSettingsActivity
```

Останній рядок — не `settings put secure enabled_notification_listeners`:
перевірено наживо, що запис лише нашого компонента система перезаписує
типовим списком слухачів, і край лишається вимкненим. `cmd notification
allow_listener` додає нас до наявного списку й не чіпає решту.

Після цього кнопка «Показати тестове сповіщення» на екрані засвітить край —
той самий шлях, яким іде звичайне сповіщення з будь-якого застосунку.
